# THE BOARD — the work queue

**This is where agents pick up work and where they report it.** One item, one
row, one owner at a time. `docs/OUTSTANDING.md` stays the ledger of what the
owner asked for — an owner ask lands there first and gets mirrored here as one
or more workable items. Bugs found by tools, assets to generate, and infra work
land here directly.

## The rules

1. **Claim before working.** Set STATUS to `IN PROGRESS` with your agent name
   and the date. Two agents on one item is wasted work.

   **AND IF YOU ARE IN A WORKTREE, YOUR NEXT-FREE ID IS A GUESS.** On
   2026-08-03 six agents ran in parallel off worktrees branched at different
   commits, and *four of them* filed rows as SG-155/156, SG-159/160/161 and
   SG-159/160/161/162 — every one of those IDs was taken by a sibling before
   the merge, and renumbering them afterwards meant rewriting IDs across code
   comments, check names, design docs and this board. The next ID is not a
   fact you can read off a stale branch. Either take a block from the person
   dispatching you, or expect to be renumbered and keep your ID in as few
   places as you can manage.
2. **DONE needs evidence, and so does every coverage claim in the docs.** A
   named harness check string, a tool output, or a commit hash — never "looks
   right". This adopts the audit rule, and it holds REPO-WIDE, DESIGN DOCS
   INCLUDED: any sentence in any `.md` (STATUS, README, the design docs, this
   board) that says the harness covers/pins/guards/asserts a behaviour must name
   the check string it means, or be marked `UNVERIFIED —` until it can. A claim
   of coverage that names no check is evidence of nothing (SG-11).
3. **Found a bug? File it before fixing it.** One row, source named, even if
   you fix it in the same session. The ledger exists because things slipped
   when nobody wrote them down.

   **3a. "THE BROWSER DID IT THIS WAY" IS NOT A REASON FOR ANYTHING.** Not for a
   mechanic, not for a visual, not for a constant. The owner retired parity as a
   goal on 2026-08-01 and hardened it to mechanics on 2026-08-03, after SG-148
   took crit away from six damage sources on fidelity grounds alone and had to be
   reverted: *"We've moved so far beyond the browser version of this game. I do
   not want you going back and trying to refer to the browser game. We've
   transcended that. We should only be focused on making the Godot version of
   this as good as possible."*

   Recording where a number CAME from is good practice and stays. Using that
   provenance as the argument for keeping it is the thing that is banned. If a
   change's whole justification is browser fidelity, stop and ask the owner —
   and if a number is right, say why it is right FOR THIS GAME. The frozen
   browser build in `reference/` is an archive and a regression yardstick
   (`tools/parity.py` — "did we lose something that was good"), never an
   authority, and the answer may legitimately be "yes, and we keep ours anyway".
4. **BLOCKED names the blocker** — a missing key, a decision only the owner can
   make, an upstream item by ID. Anything blocked on the owner is also
   mirrored, with a recommendation, in `/NEEDS_ALEX.md` at the repo root.
5. **Nothing is deleted, and THIS FILE HOLDS ONLY OPEN WORK.** The moment a row
   is DONE, CUT, DROPPED, CLOSED, RESOLVED, SUPERSEDED, CORRECTED or ANSWERED,
   cut it — with its evidence or reason intact — into
   `docs/BOARD-ARCHIVE.md`. `git log` on both files is the audit trail.

   **This is the owner's instruction, 2026-08-11**, and the reason is the size
   the file had reached: 758 KB, 233 rows, **190 of them history**. A queue
   nobody can read is not a queue. Do not re-grow it — a row that has just
   passed its gate does not "sit in Active for a while first".

   **A row that is only PARTLY resolved stays here.** "HALF DONE — STILL OPEN",
   "FIXED — PENDING VISUAL CONFIRMATION" and "three of four surfaces done" are
   open rows; the archive is for work with nothing left in it.
6. **Priorities:** P1 = blocks shipping or contradicts a written claim ·
   P2 = owner-visible improvement · P3 = worth doing, not worth doing first.
7. **Before starting anything**: read `STATUS.md`, run
   `SkyGear Tools.bat harness` (green before AND after your change), and check
   this board's IN PROGRESS rows so you don't collide.

**Where write-ups go.** `/NEEDS_ALEX.md` is a **page**, not a dossier — it holds
only what needs the owner's judgement, and it has had to be cut back from 600+
lines twice in one day. **Append your evidence to `docs/NIGHT-LOG-<date>.md`,
not to NEEDS_ALEX.** If something genuinely needs his decision, add a short
entry to its decision list and put the numbers in the log. A section he will not
read because the file is six hundred lines long is the same as not writing it.
